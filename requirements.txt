Requirements #1: Problem Understanding

System purpose:
The system manages registration for a single event with a fixed capacity while supporting a FIFO waitlist for additional users.

Inputs to the system:

Event capacity

User registration requests (register(user_id))

Cancellation requests (cancel(user_id))

Status queries (status(user_id))

Outputs produced by the system:

Updated registration state

Ordered list of registered users

Ordered FIFO waitlist

User status results (registered, waitlisted, none)

Exceptions for invalid operations

Primary goal of the system:
Ensure deterministic and consistent event registration behavior while enforcing capacity limits, preventing duplicate users, maintaining FIFO waitlist ordering, and automatically promoting waitlisted users when capacity becomes available.

Requirements #2: Assumptions

A1: Each user is uniquely identified by a user_id string.

A2: The system manages registration for one event only.

A3: Capacity is provided at initialization and does not change during runtime.

A4: Operations (register, cancel, status) occur sequentially.

A5: A user cannot appear more than once in the system.

A6: Users cannot exist simultaneously in both registered and waitlisted states.

Requirements #3: Functional Requirements

FR1: The system shall allow users to register for the event until the event capacity is reached.

FR2: The system shall place additional users into a FIFO waitlist when the event capacity is full.

FR3: The system shall automatically promote the earliest waitlisted user when a registered user cancels.

FR4: The system shall prevent duplicate registrations by raising an error if a user attempts to register more than once.

FR5: The system shall allow users to cancel their registration or waitlist position.

FR6: The system shall allow users to query their current status in the system.

Requirements #6: Edge Cases

EC1
Capacity is equal to zero.

Expected system behavior:
All users are placed in the waitlist and none are registered.

EC2
A waitlisted user cancels before being promoted.

Expected system behavior:
The user is removed and waitlist positions update accordingly.

EC3
Multiple registered users cancel in sequence.

Expected system behavior:
Waitlisted users are promoted in FIFO order until capacity is filled.

EC4
A user attempts to register again after canceling.

Expected system behavior:
The user may register again if they are no longer in the system.
